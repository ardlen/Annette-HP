# Техническое задание: система поддержки S/4HANA на DeepSeek Harness

Статус: черновик для локальной проработки.

Владелец решения: команда внедрения у конкретного владельца ERP.

Базовый runtime: DeepSeek Harness (DSH), без форка agent-loop и без внесения SAP/GraphRAG в `packages/` апстрима.

Документ фиксирует специализацию DSH под поддержку продуктивного ландшафта SAP S/4HANA: работу с проектной документацией, ТЗ, архитектурой решения и сверкой «как должно быть» с фактом системы.

Семь этапов ниже — обязательный порядок поставки; следующий этап не открывает write-контур и не расширяет роль агента, пока не принят предыдущий.

Официальные контракты DSH, на которые опирается решение: [architecture.md](../architecture.md), [mcp-client](../../packages/mcp/mcp-client/README.md), [mcp-memory](../user/guide/mcp-memory.md), [agent-instructions](../../packages/context/agent-instructions/README.md), [presets](../../packages/preset/README.md), [skills](../subsystems/skills.md), [approval](../subsystems/approval.md), [permission-presets](../../packages/interaction/permission-presets/README.md), [plan-mode](../../packages/plan/plan-mode/README.md), [webhook](../subsystems/webhook.md), [github-review example](../user/guide/github-review.md), [session-query](../subsystems/session-query.md).

## 1. Цель, объект и границы

### 1.1 Цель

Построить на DSH контур поддержки для **одного** владельца ERP: аналитик или инженер сопровождения задаёт вопрос или получает инцидент из SAP Cloud ALM, агент находит утверждённые документы с цитатой версии, при необходимости сверяет их с read-only снимком S/4 и предлагает план действий, который человек утверждает до любого изменения в QAS.

Продукт не заменяет SAP GUI, SAP Cloud ALM и службу Basis/Security; он готовит обоснованный ответ и фиксирует, на каких документах и чтениях системы он построен.

### 1.2 Объект автоматизации

- Норматив: ТЗ, FS/TS, solution architecture, процессы Signavio/BPM и контент внедрения в SAP Cloud ALM, протоколы решений, реестр интерфейсов.
- Факт системы: кастомизинг, Z/Y-объекты, IDoc, очереди, Fiori/CDS, оргструктура — только через контролируемый SAP-контур.
- Кейс: событие/инцидент SAP Cloud ALM, сессия DSH, план изменения, запись approval, аудит session JSONL.

### 1.3 Вне скоупа этой поставки

- Форк или правка agent-loop, `SessionEventMap` и shipped profiles апстрима DSH.
- GraphRAG, SharePoint, SAP SDK внутри `packages/` репозитория DSH.
- Автоматическая запись в PRD, массовый кастомизинг, транспорт в прод без человека.
- Мультитенантность нескольких владельцев ERP в одном `$DSH_HOME`.
- Извлечение PDF штатным `web_fetch` (в DSH это отложенная работа): ingest живёт в corpus-сервисе.
- MCP resources/prompts: DSH прокидывает только tools.
- Живая интеграция с SAP Solution Manager (SolMan), включая ChaRM, ITSM SolMan и Solution Documentation как операционный контур: SolMan выводится из использования.

### 1.4 Принцип архитектуры

DSH — runtime агента (профиль, пресеты, skills, approval, session log).

Корпус документов, граф решения и доступ в SAP — **внешние** сервисы за `dsh-mcp-client`.

Всё, что модель увидела из корпуса или SAP, обязано стать tool event в session log: инвариант DSH «model-visible ⟺ logged».

Три плоскости нельзя смешивать в одном индексе и в одном tool:

| Плоскость | Источник истины | Свежесть | Роль агента |
|---|---|---|---|
| Норматив | утверждённая версия документа | редкая, версионированная | цитировать |
| Факт системы | SAP (и git/gCTS, если есть) | live read | читать, не выдумывать |
| Кейс | session JSONL + SAP Cloud ALM | live | вести разбор и план |

### 1.5 Контур управления инцидентами

Инциденты и операционные события ведутся в **SAP Cloud ALM** (Implementation и Operations — те сервисы, которые уже использует владелец ERP). Это единственный живой контур кейса для webhook, MCP чтения инцидента и возврата комментария.

SAP Solution Manager **планируется к выводу**. Новые adapters, webhook и skills не строятся на SolMan, ChaRM и SolMan ITSM. Исторический экспорт SolMan (Solution Documentation, закрытые инциденты, старые change documents) допускается только как **замороженный архив** в corpus ingest, с явным статусом `superseded` / as-of на дату выгрузки, без live API SolMan.

Управление изменениями в живом контуре — сервисы SAP Cloud ALM (Change and Deployment / Features) и транспорты ландшафта (включая gCTS, если он есть), а не ChaRM.

## 2. Архитектура решения

### 2.1 Контур

```text
SAP Cloud ALM  --webhook-->  DSH profile `s4-support`
                                |  workspace = один владелец ERP
                                |  AGENTS.md ландшафта
                                |  preset: architecture | incident | change | config
                                v
                     MCP corpus (ТЗ / архитектура / граф сущностей)
                     MCP sap-read (OData/RFC, только чтение)
                     MCP alm (инцидент Cloud ALM, вложения, комментарий)
                                v
                     plan-mode + ctx.approval  -->  человек
                     PRD write запрещён permission preset
```

### 2.2 Поставка относительно DSH

Решение — **out-of-tree overlay**, не патч ядра:

- профиль `s4-support` поверх `dsh-base` (web для аналитиков; sdk/acp — если встраивание в портал);
- bundle с `cordis.patch.yml`: MCP-клиенты, пресеты, permission table, webhook adapter;
- workspace на диске: `AGENTS.md`, `.dsh/skills`, checkout кастома (abapGit/gCTS), если есть;
- отдельные процессы: corpus MCP, sap-read MCP, Cloud ALM MCP.

Монтаж MCP — как в [примере memory overlay](../user/guide/mcp-memory.md): одна строка `dsh-mcp-client` на сервер, tools вида `mcp__<serverName>__<tool>`, секреты только через credentials/env, не литералами в YAML.

Штатный MCP не скачивает сервер и не поднимает его БД; HTTP-сервисы корпуса и SAP должны быть уже запущены.

### 2.3 Изоляция владельца ERP

Один профиль / один `$DSH_HOME` / один session `cwd` = один ландшафт одного заказчика.

`session-query` авторизует cross-session доступ по точному равенству `cwd`; это граница тенанта, её нельзя ослаблять.

Карточка ландшафта (SID, клиенты, модули, запрет PRD) живёт в `AGENTS.md` этого workspace, не в process-global system prompt.

### 2.4 Канонические сущности корпуса (не свободный GraphRAG)

Индекс строится вокруг стабильных узлов решения, а не вокруг «всех сущностей, которые извлёк LLM из PDF»:

| Тип | Примеры |
|---|---|
| `Requirement` | пункт ТЗ, требование волны |
| `Process` | OTC, P2P, процесс Signavio / Cloud ALM Process Management |
| `OrgUnit` | BUKRS, WERKS, VKORG |
| `Interface` | IDoc, RFC, OData, CPI |
| `Enhancement` | BAdI, user-exit, substitution, RAP |
| `FioriApp` / `CdsView` | приложения и представления |
| `Transport` | транспорт, Cloud ALM Feature / change (не ChaRM) |
| `DocumentVersion` | документ + версия + статус + as-of |

Связи: требование → процесс → объект → система (SID) → волна; as-is / to-be / wave N — разные версии одного логического узла.

Сырой GraphRAG «по всем PDF» как единственный индекс **запрещён**.

## 3. Этапы реализации

Каждый этап имеет входные условия, артефакты и критерии приёмки.

Этап N+1 не начинается, пока N не принят.

### Этап 1. Профиль `s4-support`, workspace заказчика, `AGENTS.md` ландшафта

**Зачем.** Зафиксировать runtime, тенант и правила, которые агент видит в каждом запросе, без SAP и без корпуса.

**Сделать.**

1. Создать custom profile `s4-support` со стеком `dsh-base` + web (или sdk) по контракту [app-boot profiles](../../packages/boot/app-boot/README.md) и [bundle](../../packages/bundle/README.md).
2. Выделить workspace: абсолютный путь, `.git` как корень проекта, один cwd для всех сессий этого владельца.
3. Написать `$DSH_HOME/AGENTS.md` (глобальные запреты продукта) и цепочку workspace `AGENTS.md`: SID DEV/QAS/PRD, клиенты, модули в скоупе, tenant/URL SAP Cloud ALM, эскалация Basis/Security, правило «цитата или “не найдено”», запрет советовать write в PRD, запрет опираться на SolMan как на живую систему.
4. Подключить `@deepseek-ai/dsh-agent-instructions` с явным `maxBytes` (как в base, типично 65536).
5. Задать permission presets: как минимум `read-only` (sandbox read-only + approval `ask` или `never` для mutating shell) и `workspace-write` только для правок файлов workspace, не SAP.
6. Убедиться, что shipped coding-tools (bash write, strreplace) не могут достичь SAP; SAP отсутствует до этапа 4.

**Артефакты.** `package.json` профиля, `cordis.patch.yml`, дерево workspace, тексты `AGENTS.md`, инструкция запуска `dsh --profile s4-support`.

**Приёмка.**

- Профиль стартует; `dsh --profile s4-support --dump-config` показывает ожидаемые строки.
- Первая сессия получает durable baseline с ландшафтом заказчика (пути root-relative / `~/.dsh/AGENTS.md`).
- Вопрос вне скоупа модулей агент отвечает отказом по `AGENTS.md`, а не выдуманным кастомизингом.
- Сессия второго заказчика в этом home **не создаётся**; процедура тенанта описана как «новый home/profile».

**Не делать на этом этапе.** MCP, пресеты architecture/incident, webhook, session-query tools.

-----

### Этап 2. Corpus MCP: версии, цитаты, граф сущностей решения

**Зачем.** Дать модели поиск по ТЗ и архитектуре с обязательной цитатой `documentId + version + section`, без подмешивания графа в system prompt.

**Сделать.**

1. Поднять отдельный corpus-сервис (HTTP MCP или stdio). Ingest PDF/DOCX/HTML/Markdown — ответственность сервиса, не DSH. Живой норматив берётся из утверждённых документов и SAP Cloud ALM; выгрузка SolMan — только разовый архив с датой отсечения.
2. Хранить `DocumentVersion` со статусом `draft | approved | superseded` и полем as-of (волна / дата утверждения).
3. Построить гибридный retrieval: structured traverse по каноническим сущностям плюс FTS/vector **только по прозе** утверждённых версий.
4. Опубликовать tools (имена рабочие; в композиции они станут `mcp__corpus__*`):

| Tool | Назначение | Обязательные поля ответа |
|---|---|---|
| `corpus_search` | семантический/FTS поиск с фильтрами модуль, волна, тип документа, статус версии | список hits; пустой список — валидный ответ |
| `corpus_get` | полный кусок документа по id версии и якорю секции | текст + цитата |
| `corpus_related` | граф: требование → процессы/объекты/интерфейсы | узлы и рёбра, без «догадок» вне индекса |
| `corpus_diff` | две версии документа или ТЗ vs зафиксированный as-is snapshot | unified-смысловой diff + обе цитаты |

5. Смонтировать сервер через `dsh-mcp-client` (`transport: streamable-http` или stdio).
6. Добавить в persona/instructions пресета правило: утверждение о нормативе без вызова corpus и без цитаты запрещено; если hits пустые — явно «в корпусе не найдено».

**Контракт цитаты (каждый hit и каждый `get`).**

- `documentId`, `versionId`, `title`, `sectionAnchor` или page/clause;
- `status`, `asOf` (волна или дата);
- `uri` или стабильный locator для человека;
- фрагмент текста, достаточный для проверки, с потолком байт (spill, если смонтирован).

**Приёмка.**

- Запрос «какое требование волны 2 закрывает процесс OTC» вызывает `corpus_search` / `corpus_related` и отвечает с цитатами approved-версии волны 2, а не draft и не волны 1.
- Запрос по документу, которого нет, даёт «не найдено», а не пересказ из параметров модели.
- Повторный запрос в новой сессии того же cwd снова идёт в MCP (корпус не «запоминается» в system prompt).
- Tool results видны в session log; после compaction агент снова вызывает corpus, а не воспроизводит ТЗ из summary.

**Не делать на этом этапе.** SAP MCP, write, webhook.

-----

### Этап 3. Preset `architecture` — только документы

**Зачем.** Проверить, что агент ссылается на корпус и не выдумывает архитектуру, пока SAP ещё недоступен.

**Сделать.**

1. Каталог пресета `architecture/agent.cordis.yml`: persona архитектора решения, `agent-instructions`, `tool-skill`, MCP corpus; **без** sap-read, **без** mutating SAP, **без** web_search как замены корпуса.
2. Skills: как читать ТЗ vs FS vs architecture decision; как цитировать; что считать противоречием as-is/to-be.
3. Plan-mode можно смонтировать, но mutating tools не должны иметь SAP-целей (их ещё нет).
4. Зафиксировать snapshot-сценарии (keyless), если overlay тестируется в этом checkout: вопрос по известному fixture-документу → tool call → цитата в ответе.

**Приёмка.**

- Сессия на пресете `architecture` не видит SAP tools в каталоге.
- На fixture «процесс P2P, ТЗ раздел X» модель вызывает corpus и указывает version/section.
- На вопрос «как у нас сделан несуществующий Z-отчёт» — «не найдено в корпусе», без вымышленной таблицы.
- Токен-бюджет: схемы MCP corpus приемлемы; лишние shipped coding tools, не нужные архитектору, по возможности сняты пресетом.

**Не делать на этом этапе.** webhook Cloud ALM, session-query, SAP.

-----

### Этап 4. SAP read-only MCP и preset `incident`

**Зачем.** Сверять норматив с фактом системы: «по ТЗ должно быть X, в QAS сейчас Y».

**Сделать.**

1. Отдельный sap-read MCP. Транспорт: RFC/OData по белому списку объектов; SID и client — обязательные аргументы каждого вызова.
2. Операции только read: оргструктура, выбранный кастомизинг, статус IDoc, наличие объекта, использование CDS, выдержки ST22/SM21 по политике безопасности.
3. Секреты — `dsh-credentials` / env MCP-процесса. Stdio MCP не наследует произвольные `DSH_*` (поведение клиента); нужные переменные перечислить в `config.env`.
4. Preset `incident`: corpus + sap-read + skills разбора инцидента (OTC/P2P/R2R/IDoc) + persona «сначала цитата ТЗ, потом read системы, потом расхождение».
5. Permission preset сессии инцидента: `read-only` относительно workspace; SAP write tools отсутствуют в каталоге.
6. Запрет класть live SAP в граф корпуса: факт системы не индексируется GraphRAG.

**Приёмка.**

- Инцидент «завис IDoc» даёт: цитата процесса/интерфейса из корпуса (если есть) + read статуса в указанном SID + явное расхождение или подтверждение совпадения.
- Вызов sap-read без SID/client отвергается сервером.
- Попытка write-метода (если модель его «придумывает») не существует в schema; произвольный RFC вне allowlist отвергается.
- PRD read, если разрешён политикой заказчика, только для явно перечисленного набора; иначе только QAS/DEV.
- Логи MCP и session log позволяют аудитору восстановить, какой SID читали.

**Не делать на этом этапе.** Любой SAP write, транспорт, SPRO change.

### Этап 5. `plan-mode`, approval и webhook из SAP Cloud ALM

**Зачем.** Инцидент или событие Cloud ALM создаёт сессию; агент планирует; человек утверждает; mutating контур всё ещё закрыт.

**Сделать.**

1. Смонтировать `dsh-plan-mode` в пресетах `incident` и `change`. Учесть: plan-mode — **guidance, не enforcement**; tools остаются в каталоге. Enforcement — sandbox + `ctx.approval` (fail-closed).
2. Расширить permission table: preset инцидента `read-only` + approval `ask` на любые исключения.
3. Написать webhook adapter под доставку SAP Cloud ALM по образцу [GitHub adapter](../../packages/webhook/webhook-github/README.md) и [github-review guide](../user/guide/github-review.md): проверка подлинности по контракту CALM, `202` после in-memory dispatch, отдельный WebServer чтобы не открывать browser API.
4. Rule: verified delivery → `WebhookSessionRequest` с `workspacePath` заказчика, preset `incident`, permission `read-only`, title из id события/инцидента Cloud ALM, prompt с текстом, ссылкой на CALM и идентификаторами системы.
5. Происхождение: durable user-message с `source.kind: "webhook"` и id доставки (runtime не дедуплицирует; повторная доставка может создать повторную сессию — это принять и задокументировать).
6. MCP `alm` (опционально на этом этапе): чтение инцидента/события Cloud ALM и вложений; запись комментария обратно в CALM — только после отдельной приёмки и approval. Live API SolMan не монтировать.

**Приёмка.**

- Подписанный тестовый webhook Cloud ALM создаёт сессию в нужном workspace с нужным пресетом; неподписанный даёт 401 и не создаёт агента.
- Агент по инциденту CALM уходит в plan-mode, вызывает corpus/sap-read, вызывает `exit_plan_mode` с планом, в котором есть цитаты, SID и id события CALM.
- Согласие в чате («ок, давай») **не** считается approval plan-mode (контракт DSH).
- Пока этап 7 не принят, в плане нет шага «выполнить RFC write»; максимум «рекомендация человеку».
- Композиция не содержит MCP/webhook SolMan.

-----

### Этап 6. `session-query` и skills по модулям

**Зачем.** Повторные инциденты и процедуры модулей: «мы уже разбирали этот IDoc / этот Z-отчёт».

**Сделать.**

1. Включить FTS backend session-query для профиля (`openAt` по политике деплоя) и смонтировать `@deepseek-ai/dsh-tool-session-query` **в этом профиле** (в shipped UI DSH consumer default-off — здесь это сознательный opt-in).
2. Сохранить workspace authority: только тот же `cwd`.
3. Skills в `.dsh/skills` / `.agents/skills`: OTC, P2P, R2R, EWM, IDoc, транспорты и Cloud ALM Change and Deployment / freeze, границы Basis/Security. Каталог по требованию, не раздувать каждый запрос полными процедурами. Не добавлять skills «как работать в SolMan/ChaRM».
4. Subagents (по необходимости): один — только corpus, второй — только sap-read; родитель цитирует и собирает план. Write детям не давать.
5. Краткая instruction: перед новым разбором — `session_search` по id события Cloud ALM или номеру объекта.

**Приёмка.**

- Две сессии одного cwd: вторая находит первую по уникальному маркеру инцидента через `session_search`.
- Сессия с другим cwd тот же маркер не видит.
- Skill модуля загружается tool `skill` и меняет процедуру разбора, не подменяя цитаты корпуса.
- Модель не получает provider cursors/offset (контракт session-query tools).

### Этап 7. Write в QAS только после работающих цитат и approval

**Входные условия (все обязательны).** Этапы 2–6 приняты. На выборке инцидентов Cloud ALM агент устойчиво цитирует корпус и показывает SAP-read. Approval fail-closed проверен (нет answerer → `unavailable` → отказ). Plan-mode review работает.

**Сделать.**

1. Отдельный sap-write MCP или отдельный набор tools на том же сервере за feature-flag. Allowlist операций (узкий): например смена одной настройки в QAS, создание транспорта — только то, что заказчик явно перечислил.
2. Каждый write: обязательные аргументы SID (только QAS/DEV), client, цитаты `versionId` корпуса, которые обосновывают изменение, id плана/`exit_plan_mode`.
3. Сервер отвергает write, если SID = PRD, если нет citation ids, если операция вне allowlist.
4. DSH: `ctx.approval.request` до вызова write; исход только `allowed-once` открывает действие. Policy `never` на write-сессиях, где человека нет.
5. Preset `change`: corpus + sap-read + sap-write + plan-mode; permission не `danger-full-access`.
6. Аудит: session events + лог MCP (кто, SID, RFC, время, approval id).
7. Откат: документированная компенсация (повторный write / транспорт назад) — ответственность человека, агент только описывает шаг.

**Приёмка.**

- Write в PRD не проходит ни на MCP, ни из-за отсутствия tool в incident-пресете.
- Write в QAS без prior corpus citation отвергается MCP.
- Write без `allowed-once` не выполняется; `unavailable` не открывает шлюз.
- После успешного QAS write session log содержит approval pair, tool args с SID и citation ids, результат RFC.
- Регрессия этапов 2–4: architecture-preset по-прежнему без write tools.

## 4. Нефункциональные требования

### 4.1 Безопасность

- Секреты SAP, SharePoint и SAP Cloud ALM не попадают в YAML, session events, промпт и цитаты.
- Stdio MCP: только явно перечисленные env; не рассчитывать на полный ambient.
- PRD write запрещён на трёх независимых слоях: отсутствия tool в большинстве пресетов, allowlist MCP, approval policy.
- Чтение чувствительных данных (персонал, платежи) — отдельный allowlist и маскирование в tool result, согласованное с заказчиком.

### 4.2 Аудит и воспроизводимость

- Ответ агента по инциденту Cloud ALM должен быть восстановим из session JSONL: промпт, tool calls корпуса и SAP, план, approval, id события CALM.
- Нельзя подмешивать retrieved chunks в system prompt в обход session events.
- Compaction сжимает переписку, не корпус: после shadow агент снова вызывает MCP.

### 4.3 Свежесть и версии

- Корпус отстаёт от git и SAP Cloud ALM не больше согласованного SLO ingest (задать при внедрении, типично часы для утверждённых документов, не секунды). Выгрузки SolMan не обновляются после даты архива.
- Вопрос «как должно быть» всегда квалифицируется версией/волной; иначе агент обязан уточнить или вызвать `corpus_search` с фильтром статуса.
- Live SAP не кэшируется в графе документов.

### 4.4 Наблюдаемость

- Падение MCP: tools unregister после исчерпания reconnect (контракт mcp-client); сессия должна сообщить «корпус/SAP недоступен», а не галлюцинировать.
- Метрики: доля ответов с цитатой, доля пустых search, число approval reject, число отклонённых PRD write.

### 4.5 Совместимость с DSH

- Публичные API DSH pre-stable: overlay обновляется вместе с harness, не наоборот.
- Новые native packages в апстрим не входят, пока не появится общий capability seam с несколькими потребителями.
- UI-цитаты: host presenter на tool results (cookbook adding-a-tool), locale-owned copy, без хардкода строк в клиенте, если UI вшивается в web overlay.

## 6. Критерии приёмки продукта (сквозные)

Сквозной сценарий после этапа 5 (без write) и повтор после этапа 7 (с QAS write):

1. В SAP Cloud ALM создаётся инцидент или событие с уникальным id и ссылкой на объект (IDoc/документ).
2. Webhook Cloud ALM открывает сессию DSH в workspace заказчика на пресете `incident`.
3. Агент ищет в корпусе и цитирует approved-версию либо фиксирует отсутствие.
4. Агент читает QAS через sap-read с явным SID.
5. Агент выдает расхождение ТЗ vs факт и план через `exit_plan_mode`.
6. Человек утверждает или отклоняет план.
7. (Только после этапа 7.) Write в QAS проходит один раз после `allowed-once` и citation ids; write в PRD невозможен.

Негативные:

- Документ superseded не используется как действующая норма без явной оговорки.
- Пустой корпус ≠ «стандарт SAP устроен так-то» без оговорки, что это не ландшафт заказчика.
- Смешение двух SID в одном выводе без подписи SID — дефект.

## 7. Риски и зависимости

| Риск | Митигация |
|---|---|
| Галлюцинация кастомизинга | Этапы 2–3 без SAP; запрет ответа о нормативе без цитаты; пустой search как валидный исход |
| Stale GraphRAG по live S/4 | Live только sap-read; граф только норматив |
| Plan-mode не блокирует tools | Enforcement = approval + отсутствие write tools до этапа 7 |
| Утечка тенанта | Один home/cwd; session-query exact cwd |
| PDF/SharePoint | Ingest в corpus, не `web_fetch` |
| MCP только tools | Все документы через tools + цитаты |
| Повтор webhook | Идемпотентность на стороне rule/Cloud ALM или принятие дублей сессий |
| Опора на SolMan после вывода | Нет live API SolMan; архив только с as-of; skills и webhook только Cloud ALM |
| Pre-stable DSH | Overlay версионировать относительно pin harness |

Зависимости заказчика, без которых этапы 2/4/5 не стартуют: доступ к утверждённому архиву ТЗ, техническая учётка read QAS, tenant и API/секрет webhook SAP Cloud ALM, список модулей и волн, письменный запрет PRD, дата отсечения архива SolMan если он ещё ingest-ится.

## 8. Порядок работ и оценка трудоёмкости (ориентир)

Оценка относительная, для планирования команды из 2–4 инженеров; не контракт:

| Этап | Содержание | Ориентир |
|---|---|---|
| 1 | Профиль, workspace, AGENTS.md, permissions | 3–7 дней |
| 2 | Corpus ingest + граф сущностей + MCP + цитаты | 3–6 недель (зависит от объёма архива) |
| 3 | Preset architecture + skills цитирования + приёмка «не выдумывать» | 1–2 недели |
| 4 | sap-read allowlist + preset incident | 2–4 недели |
| 5 | plan-mode, approval, webhook SAP Cloud ALM | 1–3 недели |
| 6 | session-query + skills модулей | 1–2 недели |
| 7 | sap-write QAS, тройной запрет PRD, аудит | 2–4 недели после устойчивых цитат |

Критический путь: этап 2 (качество корпуса) определяет ценность всего контура; этап 7 без него открывать нельзя.
